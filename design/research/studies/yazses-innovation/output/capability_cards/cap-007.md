## Description

A specialised command vocabulary and integration layer targeting 3D games and simulation software, extending the XR Voice API (cap-006) with a curated set of spatial and game-interaction commands. The gaming profile defines movement, interaction, navigation, and UI command intents drawn from the conventions of mainstream 3D game genres. Commands emit structured JSON events with spatial metadata (direction vectors, target names, distances) that game engines can act on directly. Per-game vocabulary files in TOML allow developers and players to customise phrase mappings without code changes. The standard dictation path remains available for in-game text fields (chat, journal, naming), routed through the existing text injector. An example Unity scene demonstrates voice-controlled character locomotion and interaction.

## User Pain

Gamers with motor disabilities or RSI who cannot reliably use keyboard/mouse/controller have limited alternatives for 3D game input. The few existing solutions (Voice Attack, Dragon Game Commands) are Windows-only, subscription-priced, and require cloud connectivity for recognition. YazSes's offline-first model and cross-platform support are differentiators, but the standard dictation mode has no understanding of game-domain vocabulary. A developer who wants to add voice command support to their Unity game today must build the full recognition + parsing pipeline themselves. The gaming profile lowers this barrier to a single dependency and a JSON event listener. Accessibility-motivated users (Persona 3 overlap with cap-005) are the primary beneficiaries; competitive gamers seeking hands-free macros are a secondary segment.

## Proposed Solution

**Module:** `src/yazses/commands/gaming.py`

**Command vocabulary (built-in, TOML-extensible):**

```toml
# src/yazses/data/vocab/gaming_default.toml

[movement]
"move forward"     = {intent = "move", direction = [0, 0, 1]}
"move back"        = {intent = "move", direction = [0, 0, -1]}
"move left"        = {intent = "move", direction = [-1, 0, 0]}
"move right"       = {intent = "move", direction = [1, 0, 0]}
"turn left"        = {intent = "turn", degrees = -90}
"turn right"       = {intent = "turn", degrees = 90}
"turn around"      = {intent = "turn", degrees = 180}
"turn N degrees"   = {intent = "turn", degrees = "N"}  # parameterised
"jump"             = {intent = "action", action = "jump"}
"sprint"           = {intent = "action", action = "sprint", hold = true}

[interaction]
"attack"           = {intent = "action", action = "primary_attack"}
"block"            = {intent = "action", action = "block", hold = true}
"pick up"          = {intent = "interact", target = "nearest_item"}
"open"             = {intent = "interact", target = "nearest_interactable"}
"use"              = {intent = "interact", target = "equipped_item"}
"talk to [name]"   = {intent = "interact", target = "name"}

[navigation]
"go to waypoint"   = {intent = "navigate", target = "active_waypoint"}
"fast travel to [name]" = {intent = "fast_travel", destination = "name"}
"open map"         = {intent = "ui", action = "open_map"}
"mark location"    = {intent = "navigate", action = "set_waypoint_here"}

[ui]
"open inventory"   = {intent = "ui", action = "open_inventory"}
"close menu"       = {intent = "ui", action = "close_menu"}
"pause"            = {intent = "ui", action = "pause"}
"quit"             = {intent = "ui", action = "quit"}
"save game"        = {intent = "ui", action = "save"}
```

**Event structure (extends cap-006 schema):**
```json
{
  "type": "command_detected",
  "intent": "move",
  "action": "move",
  "params": {
    "direction": [0, 0, 1],
    "magnitude": 1.0
  },
  "raw_transcript": "move forward",
  "confidence": 0.98,
  "timestamp_ms": 1715692801533,
  "profile": "gaming"
}
```

**Parameterised phrase matching:**
- Phrases with `[name]` or `N degrees` markers use a two-stage match: first match the fixed frame, then extract the variable token(s) using the surrounding context.
- "fast travel to Whiterun" → `destination = "Whiterun"`.
- "turn 45 degrees" → `degrees = 45` (numeric extraction from transcript word tokens).

**Per-game vocabulary override:**
```toml
# ~/.config/yazses/games/skyrim.toml
[interaction]
"shout"        = {intent = "action", action = "dragonshout"}
"sheathe"      = {intent = "action", action = "sheathe_weapon"}
"horse"        = {intent = "action", action = "mount_horse"}
```

Applied as an overlay on top of `gaming_default.toml`. Game detection: configurable `game_name` in profile, or auto-detected via active window title matching a user-defined list.

**Dictation in game text fields:**
When the active window context signals a text input field (detectable via AT-SPI on Linux, AXRole on macOS), the gaming profile falls back to standard dictation mode with the disfluency filter (cap-004) applied.

**Unity example scene** (`sdks/unity/YazSes/Examples/VoiceLocomotion/`):
- Third-person character controller driven entirely by voice commands received via the cap-006 WebSocket.
- Demonstrates movement, interaction, inventory, and a simple NPC dialogue exchange.
- Documented with inline comments; serves as the canonical integration reference.

**Config:**
```toml
[profile.gaming]
model = "tiny.en"
commands_enabled = true
grammar = "gaming"
custom_vocab = "~/.config/yazses/games/current_game.toml"
window_title_detection = true
websocket_port = 8765
```

## Feasibility Notes

**Complexity:** Low-medium. The gaming profile builds directly on the command grammar infrastructure from cap-003 and the WebSocket server from cap-006; both must ship first. The primary new work is vocabulary curation, parameterised matching, and the Unity example scene. The Unity scene requires a developer with C#/Unity knowledge and is the highest-effort single deliverable.

**Dependencies:** Requires cap-003 (command grammar engine) and cap-006 (WebSocket server). No new Python dependencies. Unity example scene requires Unity 2022 LTS or later.

**Risks:**
- Vocabulary collision: "open" could mean "open inventory" or dictating the word "open" in a chat box. Mitigate with context detection (text field vs. game view) and a configurable command prefix key ("activate command mode with a specific hold key").
- Parameterised matching accuracy: "fast travel to the dark brotherhood" — multi-word destination extraction is harder than single-word. Implement greedy token consumption after the fixed frame, truncated at the next detected command keyword.
- Game auto-detection via window title is fragile; always allow manual override via config.

## Success Metrics

- Built-in vocabulary covers ≥90% of common commands across a test suite of 5 mainstream 3D game genres (RPG, FPS, RTS, simulation, platformer).
- Command classification latency: <5ms (rule-based, no model inference).
- False positive rate on dictation text that accidentally matches game commands: <1% on a 200-sentence natural speech corpus.
- Unity example scene: character responds to movement commands within 200ms of speech release (WebSocket round-trip included).
- Per-game TOML vocabulary loads and applies correctly with zero restart required (hot-reload on file change).
