## Description

An optional post-STT routing module that classifies transcribed text into one of three processing paths before any injection or command dispatch occurs. Simple text fragments are passed directly to the injector with no overhead. Transcripts that match known command patterns are dispatched to the rule-based grammar engine (cap-003) without LLM involvement. Transcripts that are ambiguous — matching multiple intents with similar confidence, or containing natural-language instructions that do not map cleanly to any rule — are routed asynchronously to a local LLM (Ollama or llama.cpp) for disambiguation. The LLM path is non-blocking: if no response arrives within 500ms, the raw transcript is injected immediately. The system prompt is configurable per profile, allowing the LLM's disambiguation behaviour to be tuned for coding, gaming, XR, and accessibility contexts.

## User Pain

Rule-based command grammars (cap-003) handle unambiguous commands well but fail on natural-language variations that no author anticipated: "can you go to line forty two", "I need to undo the last change", "delete everything after the cursor". These phrases convey clear intent to a human reader but match no rule or match multiple rules with similar scores. Without disambiguation, they fall through to raw dictation injection, injecting unwanted literal text into the editor. Users who speak naturally rather than using telegraphic command phrasing encounter this failure mode frequently. Cloud-based alternatives (Copilot Voice, Dragon Professional with NLP) handle natural language well but are online-only [EVIDENCE src-010] [EVIDENCE src-013]. A local LLM layer provides the same benefit without network dependency or privacy compromise.

## Proposed Solution

**Module:** `src/yazses/intents/llm_router.py`

**Three-way routing logic:**

```python
class LLMRouter:
    DICTATE_CONFIDENCE_THRESHOLD = 0.85
    COMMAND_CONFIDENCE_THRESHOLD = 0.85
    AMBIGUITY_BAND = 0.20   # two rules within this band = ambiguous

    async def route(self, transcript: str, grammar_results: list[GrammarMatch]) -> RouteDecision:
        # Fast path 1: no command keywords at all → DICTATE immediately
        if not self._has_command_keywords(transcript):
            return RouteDecision(path=Path.DICTATE, transcript=transcript)

        # Fast path 2: single unambiguous rule match → COMMAND
        if len(grammar_results) == 1 and grammar_results[0].confidence >= self.COMMAND_CONFIDENCE_THRESHOLD:
            return RouteDecision(path=Path.COMMAND, match=grammar_results[0])

        # Ambiguous: multiple matches within confidence band, or moderate-confidence single match
        top_two = grammar_results[:2]
        if len(top_two) >= 2 and abs(top_two[0].confidence - top_two[1].confidence) <= self.AMBIGUITY_BAND:
            return await self._llm_disambiguate(transcript, top_two)

        # Low-confidence single match — LLM decides between DICTATE and COMMAND
        if grammar_results and grammar_results[0].confidence < self.COMMAND_CONFIDENCE_THRESHOLD:
            return await self._llm_disambiguate(transcript, grammar_results[:1])

        # Fallback: inject as text
        return RouteDecision(path=Path.DICTATE, transcript=transcript)
```

**LLM disambiguation (`_llm_disambiguate`):**
- Fires an async request to Ollama (`http://localhost:11434/api/generate`) or llama.cpp (`http://localhost:8080/completion`).
- If no response within `timeout_ms` (default 500ms), returns `RouteDecision(path=Path.DICTATE)` — raw injection wins.
- Structured prompt forces a JSON response to avoid free-text parsing:

```python
PROMPT_TEMPLATE = """You are a voice command router for a code editor.
The user said: "{transcript}"

Possible interpretations:
{candidates_json}

Current profile: {profile}

Respond with ONLY valid JSON: {{"intent": "<intent_name_or_DICTATE>", "params": {{...}}}}
Do not explain. Do not add any text outside the JSON object."""
```

- Response is parsed with `json.loads`; any parse failure falls back to DICTATE.
- The LLM result is cached by transcript hash (LRU cache, 1000 entries, 1-hour TTL) so repeated identical phrases skip the LLM on subsequent utterances.

**Non-blocking injection flow:**
1. Rule-based grammar runs synchronously (<10ms).
2. If ambiguous: immediately start LLM async task.
3. If LLM completes within 500ms: use its decision for injection/dispatch.
4. If timeout: inject raw transcript, cancel the LLM task, log `[llm_timeout]`.
5. A `[commands.llm_async_replace]` config option (default false) enables replacing already-injected raw text with the LLM-resolved command result if it arrives late — uses the same range-select mechanism as cap-002.

**Profile-specific system prompts:**

```toml
[llm.profiles.coding]
system_prompt = "You are a voice command router for a code editor..."

[llm.profiles.xr]
system_prompt = "You are a voice command router for an XR application. Commands include navigation, object interaction, and UI control..."

[llm.profiles.gaming]
system_prompt = "You are a voice command router for a 3D game. Commands include movement, combat, inventory, and navigation..."

[llm.profiles.accessibility]
system_prompt = "You are a voice command router assisting a user with limited mobility. Interpret commands generously; prefer action over dictation when intent is plausible..."
```

**Supported LLM backends:**
- Ollama (recommended): `ollama pull llama3.2:1b` — 1B parameters, ~700MB RAM, <200ms median response on 8-core CPU.
- llama.cpp server: compatible with any GGUF model via the `/completion` endpoint.
- Both detected automatically; Ollama takes precedence if both are running.

**Config:**
```toml
[commands.llm]
enabled = false                    # opt-in only
provider = "ollama"                # "ollama" | "llamacpp"
model = "llama3.2:1b"
timeout_ms = 500
cache_size = 1000
cache_ttl_seconds = 3600
async_replace = false
```

## Feasibility Notes

**Complexity:** Medium. The routing logic itself is straightforward. The main complexity is the async timeout-and-fallback pattern, which must be implemented carefully to avoid blocking the injection hot path. The LLM prompt engineering requires iteration to achieve reliable JSON output from small models.

**Dependencies:** No new Python packages in the core module. Optional: `httpx` for async HTTP (already likely present as a transitive dependency). Ollama or llama.cpp must be installed separately by the user; document clearly.

**Risks:**
- Small LLMs (1B parameters) may produce unreliable JSON output despite the structured prompt. Mitigate: wrap in a retry loop with a 100ms retry timeout, add strict JSON schema validation, always fall back to DICTATE on parse failure.
- Ollama's first-token latency can spike to 1–2 seconds when the model is cold (not loaded in memory). Mitigate: pre-warm the model at daemon startup if LLM is enabled (`GET /api/tags` + a synthetic warmup prompt).
- Cache invalidation: a cached DICTATE decision for a phrase that the user later adds a rule for should be invalidated. Mitigate: clear the LRU cache when custom rules are reloaded.
- The `async_replace` feature requires cap-002's range-select infrastructure; gate behind a feature flag that checks whether streaming injection is available.

## Success Metrics

- LLM disambiguation accuracy on a 100-utterance ambiguous-command test set: ≥85% correct intent classification.
- LLM response latency (Ollama + llama3.2:1b, warm model, 8-core CPU): median <300ms, 90th percentile <500ms.
- Timeout fallback rate (LLM path) in production: <10% of routed utterances exceed the 500ms timeout.
- Cache hit rate after the first hour of typical use: >40% (common commands repeat).
- Zero blocking of the injection path: end-to-end latency on the DICTATE fast path unchanged (<1ms overhead) when LLM is enabled.
- `yazses doctor --check-llm` correctly diagnoses missing Ollama installation and provides the correct install command.
