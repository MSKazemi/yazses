# ADR-001: Text-Only SSH Forwarding (No Audio-Over-SSH)

## Context

cap-001 requires YazSes to work in SSH sessions, VS Code Remote SSH, and remote tmux environments. Engineers in these contexts cannot use any existing dictation tool: Superwhisper [EVIDENCE src-013], Talon [EVIDENCE src-007], and Serenade [EVIDENCE src-006] all require a local display or local audio injection target. The remote machine is typically a headless server with no audio hardware, no display server, and potentially restricted network egress.

The architectural question is where in the pipeline the system boundary between local and remote machine should be drawn. There are three plausible designs:

1. **Audio forwarding**: Stream raw microphone audio (16 kHz PCM or compressed) from the local machine to the remote machine over an SSH tunnel, run ASR on the remote machine, and inject text locally on the remote machine.
2. **Full remote install**: Install the complete YazSes stack (faster-whisper, sounddevice, model weights) on the remote machine and run it there independently.
3. **Text-only forwarding (this decision)**: Run audio capture, VAD, and ASR entirely on the local machine. Forward only the final transcribed text (or partial hypotheses in streaming mode) to the remote machine over an SSH-tunnelled connection. A minimal remote agent performs text injection only.

The decision must satisfy FR-001.1 through FR-001.7 from the PRD and particularly NFR-001.2 (no root required on either end) and NFR-001.3 (works with OpenSSH without configuration changes to the server).

## Decision

**Audio capture and ASR always run on the local machine. Only transcribed text is forwarded to the remote machine over an SSH-tunnelled JSON-RPC connection.**

The tunnel is established using OpenSSH's `-R` reverse port-forward flag, which is available in all OpenSSH versions ≥ 4.3 (2006) and requires no server-side configuration beyond `AllowTcpForwarding yes` (the default in most distributions). The local `yazses remote` CLI subprocess manages the SSH connection via `subprocess.Popen`.

The remote agent (`yazses-remote-agent`) is a standalone Python package with zero ASR dependencies. It accepts JSON-RPC `inject(text)` calls over the forwarded TCP loopback port and invokes the best available text injection backend on the remote machine (probing `xdotool`, `ydotool`, `wtype` on Linux; `SendInput` on Windows).

The text payload is plain UTF-8 JSON, typically 10–200 bytes per utterance. There is no audio data in the tunnel at any point.

## Rationale

**Why not audio forwarding (alternative a)?**

- **Latency**: RTP/PCM audio at 16 kHz × 32-bit float = 512 kbps uncompressed. On a typical WAN link (100 ms RTT), streaming audio over TCP introduces at minimum one additional RTT of buffering latency on top of the local ASR latency. Total end-to-end latency would exceed the NFR-001.1 target of 800 ms on WAN.
- **Bandwidth**: 512 kbps continuous for the duration of a recording session is nontrivial on metered or restricted corporate VPN links. Opus compression reduces this to ~32 kbps but adds the `opuslib` dependency and encoder/decoder complexity.
- **Security**: Raw audio leaving the local machine over an SSH channel means the remote sysadmin's audit logs (and any MITM on the tunnel endpoint) would contain the user's complete voice data. This violates the privacy-first posture of the product. Text forwarding exposes only the transcription output, not the biometric voice signal.
- **Complexity**: Audio forwarding requires synchronising audio codec state, handling packet loss/jitter (TCP is not ideal for real-time audio), and ensuring ASR model availability on the remote machine — which leads back to alternative b.

**Why not full remote install (alternative b)?**

- **Hardware**: Remote servers are almost universally headless; `/dev/snd` does not exist. Even if the audio capture were adapted (e.g., accept audio via IPC rather than sounddevice), the ASR model would still need to be present.
- **Model weight size**: `tiny.en` (75 MB), `base.en` (145 MB), `small.en` (465 MB) [EVIDENCE src-001]. Downloading and managing model weights on every remote machine is impractical for engineers with tens of servers.
- **Startup time**: The `FasterWhisperEngine` initialisation takes 3–8 s on a cold CPU. A remote server that users SSH into for brief sessions would incur this penalty on every connection.
- **Dependencies**: `sounddevice`, `faster-whisper`, `ctranslate2` require native libraries. Many remote servers are minimal or locked-down environments where `pip install` of binary wheels is restricted.

**Why text-only forwarding works:**

- JSON-RPC `inject(text)` payloads are tiny (10–200 bytes). On a 100 ms RTT WAN link, the one-way SSH tunnel latency contribution is approximately 50 ms, well within the 800 ms NFR-001.1 budget.
- The remote agent has no native library dependencies beyond standard Python 3.8+. It can be installed with `pip install yazses-agent` on any remote machine that has Python, or distributed as a single-file script via `yazses remote install user@host`.
- ASR accuracy is identical to local-only mode because the model runs on the user's own hardware.
- The SSH tunnel provides encryption and authentication at no additional cost (OpenSSH handles both).

## Consequences

**Positive:**
- Remote text injection latency is dominated by local ASR latency (~300 ms for tiny.en), not network latency. WAN sessions are essentially equivalent to LAN sessions.
- No user voice data leaves the local machine in any form. Privacy posture is maintained.
- The remote agent can be installed without root and without any audio or ML dependencies.
- Works with mosh (for the injection leg) because the SSH tunnel only needs to carry text; the mosh session handles terminal display independently.
- Simplifies testing: the remote agent can be tested with a mock JSON-RPC sender without any microphone.

**Negative:**
- The hold-to-talk hotkey must be detected on the local machine. This means the user must have focus on a local terminal running `yazses remote`, not on an SSH terminal in a different window. This is a known UX trade-off documented in FR-001.7 and will be addressed in a future release via a global hotkey listener that operates regardless of window focus (already present in v0.2 via `evdev` and Quartz event tap backends).
- VS Code Remote SSH injects into the VS Code editor process running locally, not into the remote shell. This is actually the desired behaviour for VS Code Remote users (the editor renders locally), but the distinction must be documented.
- Streaming partial text (cap-002) over a remote session adds one tunnel RTT to each partial hypothesis emission. This is acceptable on LAN but may produce a visible stutter on high-latency WAN links. Streaming in remote sessions is therefore marked as a v0.3.0 non-goal and deferred to a cap-002 v2 enhancement.

## Alternatives Considered

| Alternative | Reason Rejected |
|---|---|
| (a) Forward raw PCM audio to remote ASR | Latency, bandwidth, privacy, and remote hardware constraints make this impractical for the target use case. See Rationale section. |
| (b) Full YazSes install on remote machine | Requires model weights and native audio libraries on every remote server; incompatible with headless/minimal environments. |
| (c) WebSocket relay through cloud broker | Requires a cloud server, violates offline-first and privacy-first product constraints. |
| (d) X11 forwarding of the local GUI | Only works when remote machine has an X11 server; incompatible with pure SSH terminal sessions and VS Code Remote. |
