# ADR-005: Accessibility via Config Parameters First, LoRA Fine-Tune Second

## Context

cap-005 requires YazSes to serve users with atypical speech — including people with ALS, Parkinson's disease, dysarthria, hypophonia, and motor disabilities that affect keyboard use. Voiceitt [EVIDENCE src-008] and academic research on adaptive ASR interfaces [EVIDENCE src-010] establish that this population's primary barriers to using off-the-shelf voice tools are:

1. **VAD threshold mismatch**: Standard silence detection (RMS threshold = 0.01 in `audio/vad.py`) is calibrated for typical adult speech. Users with hypophonia (reduced voice intensity) or unusual phonation onset patterns (e.g., ALS-related breathy onset) are frequently cut off or not detected.
2. **Pre-speech padding**: Standard recorders start capturing at hold-key time. Users with delayed phonation — who need a moment after pressing the key before they can produce voiced sound — lose their sentence-initial phonemes.
3. **Hold-key accessibility**: Users with motor disabilities may not be able to hold a keyboard key. Footpedals, adapted switches, and joystick buttons are standard assistive technology in this population.
4. **Model accuracy**: The `tiny.en` model has a word error rate approximately 2× higher than `base.en` on non-standard speech [EVIDENCE src-009]. Users with dysarthria benefit significantly from larger models.
5. **Personalised acoustic model**: The state-of-the-art solution for atypical speech is speaker adaptation — LoRA fine-tuning of the Whisper encoder on the user's voice samples — as demonstrated by Voiceitt [EVIDENCE src-008] and studied in adaptive XR interfaces [EVIDENCE src-010].

The architectural question for v0.3.0 is: how much of the accessibility solution can be delivered without a training pipeline?

## Decision

**MVP (v0.3.0): Deliver accessibility accommodations as config parameters and a VAD auto-tuning enrollment wizard. LoRA fine-tuning of the Whisper encoder is deferred to v0.4.0.**

The v0.3.0 accessibility feature set is:

1. **`recording.min_silence_ms`** (default 500 ms; range 200–5000 ms): Configures the trailing-silence window before recording stops. Users with slow or interrupted speech extend this to prevent premature cutoff.

2. **`recording.pre_speech_padding_ms`** (default 200 ms; range 0–2000 ms): Implemented in `audio/padding.py` as a ring buffer that prepends the last N ms of audio to each recording. Captures sentence-initial phonemes for users with delayed phonation onset.

3. **Alternative hold-key input sources** (`hotkey.source = "evdev"`, `hotkey.evdev_device = "/dev/input/eventN"`): Allows footpedals, adapted switches, and joystick buttons as hold-to-talk triggers on Linux via the evdev subsystem. The `platform/linux/hotkey.py` backend already uses evdev [EVIDENCE src-011]; this adds device path configurability.

4. **ASR model selection** (`stt.model = "tiny.en" | "base.en" | "small.en"`): Already supported by `FasterWhisperEngine`; surfaced in accessibility documentation as a recommended upgrade for non-standard speech [EVIDENCE src-009].

5. **Enrollment wizard** (`yazses enroll`): Interactive CLI in `accessibility/enroll.py` that records 20 calibration utterances, computes the user's personal noise floor and speech RMS statistics, and writes derived `vad_threshold`, `min_silence_ms`, and `pre_speech_padding_ms` values to `config.toml`. Does not train a new model.

6. **Auto-enabled disfluency filter** (cap-004): The accessibility profile pre-enables the disfluency filter with an extended filler list that includes non-standard vocalisations common in atypical speech (e.g., extended "um", glottal stops represented as silence gaps).

LoRA fine-tuning — training a set of Whisper encoder adapter weights on the user's calibration utterances — is documented as a v0.4.0 commitment in the roadmap but is not implemented in v0.3.0.

## Rationale

**Why not ship LoRA in v0.3.0 (alternative a)?**

LoRA (Low-Rank Adaptation) of the Whisper encoder is technically sound [EVIDENCE src-009, src-010]: a small set of adapter matrices (typically 0.1–1% of model parameters) is trained on a few hundred user-specific utterances, adapting the model to the user's voice without full retraining. The approach is used in production by Voiceitt [EVIDENCE src-008].

However, shipping LoRA in v0.3.0 requires:

1. **Training pipeline**: A `peft`/`trl` LoRA training loop, a compatible version of `transformers` (for the Whisper model class — faster-whisper uses CTranslate2, not Hugging Face transformers), and a CTranslate2 adapter merge step. The `peft` library alone adds 35+ transitive dependencies.
2. **Data collection**: 20 calibration utterances (the enrollment wizard) produce approximately 60–120 s of audio. LoRA training on Whisper requires 10–30 minutes of labelled audio for meaningful adaptation [EVIDENCE src-009]. The enrollment wizard as designed for v0.3.0 does not collect enough data for LoRA.
3. **Hardware**: LoRA training on the smallest Whisper model (`tiny.en`) requires approximately 2 GB of RAM and 5–20 minutes on a modern CPU. This is feasible but long; users expect enrollment to complete in ≤10 minutes (NFR-005.1), which is incompatible with training on the data collected in that session.
4. **CTranslate2 adapter support**: faster-whisper uses CTranslate2 for inference. As of the v0.3.0 timeline, CTranslate2's support for running LoRA adapters at inference time is experimental and not part of the stable API. A v0.4.0 timeline allows this API to stabilise.

Estimate: implementing a production-quality LoRA training pipeline, enrollment data collection, adapter management, and inference integration would require 3+ weeks of engineering effort — exceeding the v0.3.0 scope boundary.

**Why not ship a Voiceitt-style mobile enrollment app (alternative b)?**

Voiceitt [EVIDENCE src-008] uses a mobile app to collect speech samples in a guided session, then trains a cloud model. Building a mobile app is entirely out of scope for a daemon-centric CLI tool. The v0.3.0 target user base explicitly requires an offline, CLI-accessible workflow (NFR-005.2).

**Why not skip accessibility in v0.3.0 (alternative c)?**

This alternative is explicitly rejected on ethical and regulatory grounds. The EU European Accessibility Act (EAA) 2025, effective June 2025 [EVIDENCE src-008], requires software products placed on the EU market to meet accessibility requirements under EN 301 549. While dictation tools are not explicitly listed in the EAA's product scope, the trajectory of accessibility legislation and YazSes's stated positioning as an "accessibility-first" alternative to Superwhisper [EVIDENCE src-013] and Talon [EVIDENCE src-007] means that shipping v0.3.0 with no accessibility accommodation would be inconsistent with the product's own PRD (target persona P3) and with applicable regulatory expectations.

Additionally, the config-parameter approach (items 1–4 above) is extremely low implementation cost: the parameters already exist in the data model (`SttConfig.model`, `AudioConfig.sample_rate`, `AudioConfig.max_record_seconds`), and adding `vad_threshold`, `min_silence_ms`, `pre_speech_padding_ms`, and `evdev_device` is a small extension to `config.py` and the audio subsystem. The enrollment wizard is ~180 LOC and represents a meaningful user experience improvement for zero-dependency cost.

**Why the config-parameter approach is the right v0.3.0 MVP:**

- The enrollment wizard delivers personalised VAD tuning without any training dependency.
- The footpedal/adapted-switch support (`evdev_device`) is the single highest-impact accessibility feature for motor-disabled users and costs ~20 LOC in the Linux hotkey backend.
- Model selection (`base.en` vs `tiny.en`) is already implemented; it just needs to be surfaced in accessibility documentation and in `yazses doctor --accessibility`.
- All v0.3.0 accessibility features are non-breaking and additive: the config schema has safe defaults, so existing users are unaffected.

## Consequences

**Positive:**
- All v0.3.0 accessibility features require zero new Python package dependencies.
- The enrollment wizard can be tested end-to-end in CI using a synthetic audio fixture — no real microphone required in tests.
- Users with motor disabilities can immediately benefit from footpedal support on Linux (evdev_device config).
- The `yazses doctor --accessibility` command provides a clear, actionable checklist that guides users to the right settings without requiring support tickets.
- The v0.3.0 implementation lays the groundwork for v0.4.0 LoRA: the enrollment wizard's 20-utterance calibration session can be extended to collect the 50–100 labelled utterances needed for LoRA without changing the UX flow.

**Negative:**
- Users with severe dysarthria (significantly deviant phoneme distributions) will not see the accuracy improvements that LoRA would provide. The `base.en` model with enrollment-tuned VAD is a partial solution; WER may still be 2–3× higher than for typical speech [EVIDENCE src-009].
- The 20-utterance enrollment session is designed for VAD calibration, not model training. The utterances are not labelled (no ground-truth transcription is stored). If v0.4.0 LoRA training requires labelled data, users will need to re-enroll. This is an accepted trade-off documented in the v0.4.0 planning notes.
- The footpedal support is Linux-only in v0.3.0. macOS and Windows equivalents (HID input via IOKit on macOS, Raw Input API on Windows) are deferred to v0.4.0 along with LoRA.
- `min_silence_ms` and `pre_speech_padding_ms` require changes to `AudioRecorder` and `audio/vad.py` call sites in `core/daemon.py`. These are low-risk changes but do touch the audio pipeline, requiring careful testing on all three platforms.

## Alternatives Considered

| Alternative | Reason Rejected |
|---|---|
| (a) Ship LoRA fine-tuning in v0.3.0 | Requires 3+ weeks of engineering effort; training pipeline adds 35+ transitive dependencies; CTranslate2 adapter API is not stable; 20 calibration utterances insufficient for meaningful LoRA adaptation. |
| (b) Voiceitt-style mobile enrollment app | Requires mobile app development; cloud training pipeline; incompatible with offline-first and CLI-accessible design requirements. [EVIDENCE src-008] |
| (c) No accessibility support in v0.3.0 | Contradicts target persona P3 (accessibility users) in the PRD; inconsistent with product positioning relative to EU EAA 2025 accessibility trajectory [EVIDENCE src-008]; high impact features available at negligible cost. |
| (d) Ship static disability presets (e.g., "ALS profile", "Parkinson's profile") | Presets based on population statistics are not personalised enough; voice characteristics vary widely within each disability group. Enrollment-based calibration is strictly better at the same implementation cost. [EVIDENCE src-010] |
