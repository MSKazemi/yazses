# ADR-003: Grammar-Rule Intent Classifier (No Dedicated Coding ASR Model)

## Context

cap-003 requires YazSes to recognise a set of code-editing and terminal voice commands from transcribed text (e.g., "delete last three words", "go to line 42", "undo that") and dispatch them as structured intents. The core design question is: at which stage of the pipeline should command recognition occur, and what technique should be used?

Two fundamentally different approaches are available:

**Model-level approaches**: Replace or augment the ASR model itself with a model trained on coding vocabulary. Serenade [EVIDENCE src-006] uses a dedicated deep-learning speech-to-code model trained on programming-specific phoneme distributions. An alternative is to fine-tune Whisper on a corpus of voiced code commands.

**Text-level approaches**: Run the standard general-purpose ASR (Whisper) and classify the resulting text with a post-processing step. This includes regex/grammar classifiers (Talon-style [EVIDENCE src-007]), n-gram LMs, or LLM-based intent classifiers.

The decision interacts with several constraints from the PRD:

- FR-003.2: Classifier runtime budget <5 ms per transcript.
- FR-003.4: Unrecognised text falls through to DICTATE with zero user interruption.
- FR-003.6: User-configurable custom commands via config.toml.
- NFR-003.1: Command recognition precision ≥ 90% on the MVP command set.
- NFR-003.2: Zero false-positive command triggering on a 500-word dictation-only corpus.

## Decision

**Code commands are detected via a regex/keyword grammar classifier applied to transcribed text (`src/yazses/commands/grammar.py`). No dedicated coding ASR model, Whisper fine-tune, or LLM classifier is used.**

The classifier is implemented as a `GrammarSpec`: an ordered list of compiled `re.Pattern` objects, each paired with an `IntentType` tag and a named-group extraction spec for arguments (e.g., line number N, word count N, symbol name). Patterns are evaluated in priority order; the first match wins. Unmatched text returns `IntentType.DICTATE`.

Each pattern in the default MVP grammar maps to a row in FR-003.3's command table. Examples:

```python
(re.compile(r'\bdelete\s+last\s+(?P<n>\d+|one|two|three)\s+words?\b', re.I),
 IntentType.EDIT, "delete_words"),
(re.compile(r'\bgo\s+to\s+line\s+(?P<n>\d+)\b', re.I),
 IntentType.NAVIGATE, "go_to_line"),
(re.compile(r'\bundo(?:\s+(?:that|(?P<n>\d+)\s+times?))?\b', re.I),
 IntentType.EDIT, "undo"),
```

User-configurable custom commands from `[[commands]]` stanzas in `config.toml` are compiled into additional `re.Pattern` entries appended to the grammar list at startup.

Per-application profiles (`[commands.profiles.*]`) load a separate ordered pattern list that is prepended before the default grammar, allowing application-specific commands to take priority.

The `classify()` function is stateless and thread-safe; it holds no references to audio data or model state.

## Rationale

**Why not a dedicated coding ASR model (Serenade, alternative a)?**

Serenade's speech-to-code model [EVIDENCE src-006] is specifically designed for this problem and achieves high accuracy on its training distribution. However:

- **Closed source**: Serenade's model weights and architecture are proprietary. YazSes cannot bundle, redistribute, or modify them.
- **Separate download**: Even if licensing permitted it, the model is a separate multi-hundred-MB download, contradicting the lightweight, offline-installable posture of YazSes.
- **Domain shift**: Serenade's model is optimised for Serenade's own command vocabulary. Customisation (FR-003.6) and profile-specific commands (FR-003.7) would require fine-tuning, which is impractical for end users.
- **English-only**: Serenade's coding model is English-only. A grammar-rule classifier is trivially extensible to other languages by swapping the pattern list.

**Why not fine-tune Whisper on coding vocabulary (alternative b)?**

Whisper fine-tuning for command recognition has been explored in the literature [EVIDENCE src-009]. The approach involves collecting a labelled corpus of voiced code commands and fine-tuning the Whisper encoder-decoder on that corpus. The problems:

- **Model size and packaging**: A fine-tuned Whisper model is 75–465 MB depending on the base size. Distributing it adds a model download step to cap-003's installation, conflicting with the design goal of zero-download cap-003 activation.
- **High complexity**: The fine-tuning pipeline (dataset preparation, PEFT/LoRA setup, evaluation harness) is estimated at 3+ weeks of engineering effort — a cost already explicitly rejected in the PRD's deferral of LoRA for cap-005.
- **Overfitting risk**: A fine-tuned model trained on a fixed command corpus will generalise poorly to user-specific pronunciations, regional accents, and custom command phrases (FR-003.6). The grammar classifier degrades gracefully to DICTATE on unseen phrases; the fine-tuned model would generate hallucinated command-like text instead.
- **Defeats offline-lightweight constraint**: YazSes's core value proposition is that it runs on CPU without GPU or large model downloads [EVIDENCE src-001]. Adding a second model for commands directly contradicts this.

**Why not an LLM classifier (alternative c)?**

Local LLMs (Ollama, llama.cpp) can perform intent classification with high accuracy. However:

- **Latency**: Even quantised 7B models take 200–600 ms for a single inference on CPU, far exceeding the FR-003.2 budget of <5 ms. Command dispatch must feel instantaneous; 200+ ms delay on every utterance (including DICTATE fallthrough) would be perceptible and frustrating.
- **Startup dependency**: Requiring Ollama to be running for command recognition to work creates a hard dependency that must be checked at startup, adding complexity to `yazses doctor` and the daemon build phase.
- **False positive risk**: LLMs are prone to semantic over-generalisation. A sentence like "I want to delete the last paragraph of this report" might match EDIT/delete even though it is clearly dictation text, not a command. The regex classifier's precision on the closed MVP command set (NFR-003.1) is provably ≥ 90% because the patterns are designed for the exact command surface.

**Why the grammar-rule classifier is sufficient:**

Talon Voice [EVIDENCE src-007] — the most widely deployed open-source voice coding tool — uses exactly this approach: a hierarchical grammar of compiled regex patterns covering a large vocabulary of programming commands, with DICTATE fallthrough. Talon's user community has proven that this technique scales to hundreds of custom commands across dozens of applications with no accuracy degradation. The grammar-rule approach has the following properties relevant to the MVP requirements:

- Precision on the closed command set is provably high because the patterns are designed for the exact phrases in FR-003.3's command table and anchored with word-boundary assertions (`\b`), preventing partial-string false positives.
- False-positive rate on dictation corpora is controlled by requiring that command patterns be grammatically distinct from normal prose (imperatives starting with specific verbs, followed by optional numeric arguments).
- Runtime is O(k × n) where k is the number of patterns and n is the text length. With k = 30 MVP patterns and n ≤ 200 characters, this is trivially under 1 ms, far below the 5 ms budget.
- Zero new dependencies; zero model downloads. cap-003 activates automatically when `commands.enabled = true` in config.toml.

## Consequences

**Positive:**
- Zero new runtime dependencies for cap-003.
- Custom commands (FR-003.6) and per-app profiles (FR-003.7) are first-class features with no retraining required — users add a TOML entry and restart the daemon.
- The classifier is stateless and thread-safe, making it safe to call from the streaming transcription path without locking.
- The DICTATE fallthrough (FR-003.4) is a no-op code path: if no pattern matches, `classify()` returns immediately with the original text, adding exactly 0 ms to injection latency in the common case.
- The grammar can be unit-tested exhaustively against the FR-003.3 command table with a simple `pytest` parametrise fixture. No ASR inference is needed in tests.

**Negative:**
- The classifier operates on text output from Whisper, not on audio features. If Whisper mishears "go to line 42" as "go to lime 42", the pattern will not match and the text will fall through to DICTATE. The user must repeat the command. This is a known limitation of text-level classifiers and is acceptable given that NFR-003.1 requires ≥ 90% precision (not ≥ 90% recall) — false negatives (missed commands) are less damaging than false positives (unintended commands executed during dictation).
- Number word recognition ("three", "two") must be handled explicitly in patterns or via a numword-to-digit normalisation step in `grammar.py`. This is ~30 lines of normalization code but is not a dependency.
- Multilingual support requires translating pattern lists into each target language. This is deferred to a future release; v0.3.0 is English-only (consistent with Whisper's `language="en"` setting in `FasterWhisperEngine`).

## Alternatives Considered

| Alternative | Reason Rejected |
|---|---|
| (a) Serenade's speech-to-code model | Closed source; separate model download; not customisable; English-only. [EVIDENCE src-006] |
| (b) Whisper fine-tune on coding vocabulary | 3+ weeks engineering effort; adds second model download; overfitting risk on custom commands; conflicts with offline-lightweight constraint. [EVIDENCE src-009] |
| (c) Local LLM classifier (Ollama) | 200–600 ms latency per utterance on CPU; hard dependency on Ollama running; semantic over-generalisation produces false positives. |
| (d) Vosk grammar FST | Vosk supports runtime-configurable grammar FSTs for command detection. However, adding Vosk as a second ASR engine (alongside faster-whisper) doubles the ASR dependency surface and requires separate model downloads. Rejected on packaging complexity grounds. |
