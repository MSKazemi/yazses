# ADR-002: LocalAgreement Policy for Streaming Partial Hypotheses

## Context

cap-002 requires the daemon to emit partial transcription text to the active window as the user speaks, targeting a first-partial latency of ≤600 ms (NFR-002.1). The fundamental challenge is that Whisper — including faster-whisper [EVIDENCE src-001] — is not a streaming model. It is trained on complete audio segments. When applied to a growing audio buffer, early decode results are unstable: words near the end of the current buffer are frequently revised in the next decode pass as more audio context becomes available. This instability is well-documented in the whisper_streaming codebase [EVIDENCE src-002].

If partial hypotheses are injected into the active window and are later revised, the user sees text flickering, being deleted, and being retyped — a worse experience than simply waiting for the final result. The architecture must therefore define a policy for deciding which substrings of a partial hypothesis are sufficiently stable to emit.

Three candidate policies were considered:

1. **Emit every decode result**: On every 300 ms decode tick, replace all injected partial text with the new hypothesis.
2. **Fixed time window**: Emit only the text decoded from audio older than a fixed window (e.g., "text decoded from audio > 1.5 s ago is stable").
3. **LocalAgreement confirmation policy** [EVIDENCE src-003]: A text prefix is considered stable and emitted only after it has appeared identically in two or more consecutive decode passes.

## Decision

**Use the LocalAgreement 2-iteration confirmation policy from whisper_streaming (Macháček et al., 2023) [EVIDENCE src-003] to decide when to emit stable prefixes during streaming.**

Implementation: `src/yazses/stt/streaming.py` maintains a `_prev_hypothesis: str` field. On each decode tick (every `config.streaming.partial_interval_ms` ms, default 300 ms):

1. Decode the full rolling audio buffer with `WhisperModel.transcribe()`.
2. Compute the longest common prefix between the new hypothesis and `_prev_hypothesis`.
3. The common prefix is the stable prefix. Emit only the characters of the stable prefix that have not already been emitted (delta since last emission).
4. Update `_prev_hypothesis = new_hypothesis`.

This is the "2-iteration" variant: a prefix is confirmed after appearing in 2 consecutive decodes (the current decode agreeing with the previous decode). The whisper_streaming paper reports this variant achieves a Latency-adjusted LLSS (Local Latency-Sensitive Score) of 0.3 s on average English speech at the base.en model size [EVIDENCE src-003], which satisfies NFR-002.1 (≤600 ms first partial).

The implementation reuses the existing `FasterWhisperEngine._model` instance; no second model is instantiated. The streaming decode runs in a background thread (not the main hotkey thread) to avoid blocking the hold-key event loop.

## Rationale

**Why not emit every decode result (alternative a)?**

The core problem with emitting every raw decode result is that Whisper's attention mechanism causes instability at the acoustic boundary of the current buffer: the last 0.5–1.5 s of decoded text is frequently revised in the next decode pass as more audio provides context for phoneme disambiguation [EVIDENCE src-003]. In practice, this means:

- The injected text flickers: words appear, disappear, and are replaced multiple times per second.
- Each revision requires deleting previously injected characters (backspace sequence) and reinjecting new ones, multiplying keypress events by a factor of 3–5 compared to the LocalAgreement approach.
- The injection backend (xdotool, ydotool) queues keypress events; rapid delete-retype cycles can desynchronise the queue on slow machines.
- WhisperPipe's 2026 benchmarks [EVIDENCE src-004] show that raw hypothesis emission produces a flicker rate of 4.2 revisions/second on average English speech — perceptually equivalent to a typewriter effect that obscures the cursor position.

**Why not a fixed time window (alternative b)?**

A fixed time window (e.g., "emit text decoded from audio > T seconds ago") appears simple but has a fundamental flaw: speech rate varies. A user speaking at 2 words/second would have 4 words "aged out" of the window per emission interval; a user speaking at 6 words/second (fast speech) would have 12 words. The window must be tuned per-user and per-utterance context, and there is no signal available to do so without VAD information about word boundaries.

Additionally, a fixed window introduces a guaranteed latency floor: if T = 1.5 s, the user will never see partial text for the most recent 1.5 s of speech, which violates the spirit of NFR-002.1 (the first partial should appear quickly; stable text should also appear quickly once it is stable, not after an arbitrary delay).

The LocalAgreement policy is adaptive: it emits text as fast as the model can confirm stability, which correlates with speech rate and model confidence rather than a fixed clock.

**Why LocalAgreement is the right choice:**

- It is published, peer-reviewed science [EVIDENCE src-003] with open-source reference implementation [EVIDENCE src-002].
- The 2-iteration variant has O(n) complexity in hypothesis length, well within the <5 ms budget per decode tick on modern hardware.
- It degrades gracefully: if the model is uncertain about a region (e.g., technical jargon), those tokens simply remain in the "unstable" region longer and are emitted as part of the final correction. No additional logic is needed for uncertain regions.
- It is model-agnostic: the same policy would apply if the STT backend is replaced in a future version.

## Consequences

**Positive:**
- Partial text emitted to the active window is stable: once injected, it will not flicker or be revised mid-emission (only the final correction on hotkey release may change it).
- The policy naturally handles all speech rates, including fast speakers who would saturate a fixed-window approach.
- No additional model or dependency is introduced. The existing `FasterWhisperEngine._model` is reused.
- The correction-on-commit step (ADR-004) only needs to replace the delta between the last stable emission and the final transcript, minimising keypress events.

**Negative:**
- Stable prefix detection requires two decode passes before any text is emitted. On the `tiny.en` model at 300 ms intervals, the first stable partial appears at approximately 600 ms after speech onset, which is exactly at the NFR-002.1 boundary. Users with slow machines may occasionally breach this limit; `partial_interval_ms` is configurable to allow tuning.
- The rolling buffer grows throughout the recording session. After ~30 s, decode latency on `tiny.en` may exceed 300 ms on slow hardware. The buffer is capped at `config.audio.max_record_seconds` (default 90 s) to bound this; in practice, most utterances are under 15 s.
- The common-prefix comparison is byte-exact (case-sensitive, punctuation-sensitive). Whisper occasionally varies capitalisation or punctuation between passes (e.g., "Hello" vs "hello") while keeping the semantic content stable. In these cases, the common prefix is shorter than it could be, causing a slightly higher revision rate. This is an acceptable approximation; a tokeniser-level comparison would be more accurate but would require exposing Whisper's token IDs through faster-whisper, which is not a stable API.

## Alternatives Considered

| Alternative | Reason Rejected |
|---|---|
| (a) Emit every raw decode result | Unacceptable flicker rate (4.2 revisions/s [EVIDENCE src-004]); excessive keypress event generation causing injection queue desynchronisation. |
| (b) Fixed time window | Insensitive to speech rate; introduces guaranteed latency floor that is not adaptive; requires per-user tuning. |
| (c) WhisperX alignment-based word timestamps | WhisperX [EVIDENCE src-005] provides word-level timestamps but requires the `pyannote.audio` alignment model as a dependency (300+ MB additional download), which contradicts the lightweight packaging constraint. |
| (d) 3-iteration LocalAgreement | Would reduce false-stable emissions but increases first-partial latency to ~900 ms (3 × 300 ms intervals), violating NFR-002.1. |
