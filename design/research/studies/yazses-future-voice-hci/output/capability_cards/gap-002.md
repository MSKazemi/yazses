# Code-Aware Voice Dictation via LSP Context Injection

---

## Capability Description

Every developer who uses voice dictation for coding today faces the same problem: the transcription engine has no idea they're writing Python, that the cursor is inside a class method named `process_batch`, or that the codebase uses `snake_case` throughout. The result is mangled output — camelCase where snake_case belongs, wrong symbol names, and constant correction cycles that erase the productivity benefit of voice input.

This capability connects YazSes to the Language Server Protocol (LSP) client running in the user's editor. When the user holds the hotkey and speaks, the daemon reads the current file language, cursor position, active symbol scope, and recently declared identifiers from the LSP, and injects this structured context into the faster-whisper transcription prompt. The engine now transcribes with awareness of the codebase vocabulary.

Developers no longer need to spell out variable names phonetically or correct case mismatches after every utterance. Voice dictation becomes viable for writing real code, not just prose comments.

---

## Underlying Mechanism

**LSP context extraction:** An `LspContextProvider` class establishes a JSON-RPC connection to the running LSP server for the active editor. It issues `textDocument/hover`, `textDocument/documentSymbol`, and `workspace/symbol` requests at the current cursor position to extract: (1) file language ID; (2) enclosing function/class scope; (3) recently used identifiers within the active file (top-20 by proximity to cursor). This context is assembled into a compact string injected into the faster-whisper `initial_prompt` parameter. [HYPOTHESIS]

**Editor-agnostic connection via editor bridge:** Each supported editor exposes LSP information through a different mechanism. The `LspContextProvider` implements an `EditorBridge` protocol with per-editor backends: `NeovimBridge` (reads from `nvim --headless` RPC socket), `VsCodeBridge` (reads from the VS Code extension API via a companion extension), `EmacsLspBridge` (reads from `lsp-mode` over STDIO). The `EditorBridge` protocol is simple: `get_context() -> CodeContext | None`. [HYPOTHESIS]

**faster-whisper initial_prompt injection:** The `SttConfig` gains a `code_context_provider: str | None` field. When set, the daemon calls `context_provider.get_context()` before each recording session and constructs the Whisper `initial_prompt` string: `"Language: Python. Scope: class BatchProcessor, method process_batch. Recent identifiers: batch_size, record_count, timestamp_utc."` This prompt biases the beam search decoder toward these tokens. [EVIDENCE src-001] Transcription accuracy for domain-specific vocabulary improves significantly when in-context terminology is provided in the initial prompt.

**Combination with cap-001 LLM intent routing:** When cap-001 is also active, the LSP code context is additionally injected into the Tier 2 SLM prompt, enabling the intent router to distinguish between "open parenthesis" (dictation command) and "call this function" (code navigation command) based on the current code state. [HYPOTHESIS]

## Evidence Basis

- [EVIDENCE src-002] VoiceBench includes a coding task category, but no evaluated voice system achieves notably higher quality on coding vs. other tasks — because no system provides code-context injection to improve transcription accuracy. This is the direct statement of the gap this capability closes.
- [EVIDENCE src-001] The XR multimodal survey identifies "typing" as a rapidly growing voice task in XR contexts; code-specific evaluation is absent from all 12 XR papers reviewed. The gap is universal across both desktop and XR voice research.
- [EVIDENCE src-010] The ICMI systematic review identifies context injection (from gaze, gesture, or ambient signals) as the mechanism that most improves voice command disambiguation across 50 surveyed systems. LSP context is the coding domain's equivalent of the gaze context that speech+gaze systems use.
- [HYPOTHESIS] The faster-whisper `initial_prompt` parameter (a standard Whisper API feature) is the correct injection point for this context: it conditions the beam search decoder on domain vocabulary without requiring a custom acoustic model or fine-tuning.
- [HYPOTHESIS] Language Server Protocol (LSP) is supported by all major editors (VS Code, Neovim, Emacs, JetBrains) and provides structured, queryable code context through a standardised JSON-RPC interface. No existing voice tool exploits this interface.

## User Value Proposition

**Target persona:** Software developer using voice dictation during long coding sessions (RSI management, hands-free coding, accessibility). Currently using YazSes or a generic dictation tool for code comments and documentation, but reverting to keyboard for actual code due to transcription errors.

**Current pain:** Variable names transcribe as prose words ("process batch" instead of `process_batch`); camelCase/snake_case conventions are ignored; symbols from the current codebase are not in the transcription engine's vocabulary, requiring manual correction after every utterance. Correcting these errors often takes longer than typing the code manually, eliminating the value of voice input for actual code.

**Improvement this capability delivers:**
- Symbol names from the active file and scope are recognised correctly on first transcription, reducing per-utterance correction rate from ~40% to an estimated <10% for in-scope identifiers. [HYPOTHESIS]
- Language-specific conventions (snake_case in Python, camelCase in TypeScript) are inferred from the LSP language ID and reflected in transcription output. [HYPOTHESIS]
- Developers can dictate code at natural speaking pace without spelling out identifiers — the LSP vocabulary bias means "process batch" is interpreted as `process_batch` based on the visible scope. [HYPOTHESIS]

**So that:** developers can dictate real code at natural speaking speed without a post-transcription correction pass for identifiers and naming conventions.

## Technical Approach

**Data model:** A `CodeContext` dataclass is introduced: `{language_id: str, file_path: str, scope_chain: list[str], recent_identifiers: list[str], cursor_line: int}`. This is assembled by `LspContextProvider` and consumed by both the STT pipeline (`initial_prompt` injection) and the SLM intent router (cap-001 context augmentation). [HYPOTHESIS]

**API surface:** `LspContextProvider` is an optional daemon component: `core/daemon.py` creates it if `CommandsConfig.lsp_enabled` is `True` (default: `False`). The provider exposes one method: `get_context(timeout_ms: int = 50) -> CodeContext | None`. A timeout of 50 ms ensures LSP latency never blocks the recording pipeline; if the context is unavailable within the timeout, transcription proceeds without it (degraded-graceful). [HYPOTHESIS]

**Integration points:**
- `stt/faster_whisper.py`: `initial_prompt` parameter receives the formatted context string from `CodeContext` before each decode call. [HYPOTHESIS]
- `commands/slm_router.py` (cap-001): the `CodeContext` is serialised and appended to the Tier 2 SLM prompt when both capabilities are active. [HYPOTHESIS]
- `config.py CommandsConfig`: new fields `lsp_enabled: bool = False`, `lsp_editor: str = "auto"` (auto-detect from running processes). [HYPOTHESIS]
- `platform/linux/lsp.py`, `platform/macos/lsp.py`: editor-specific bridge implementations. [HYPOTHESIS]

**Key technical questions before coding:**
1. How does the `VsCodeBridge` communicate with VS Code — via the official VS Code extension API (requires a companion extension in the VS Code marketplace) or via the VS Code CLI `--locate-extension-host` socket? The companion extension approach is more powerful but requires a separate shipping artefact.
2. Does the Whisper `initial_prompt` injection actually improve identifier accuracy on code, or does the standard vocabulary already handle common patterns? This requires a controlled experiment comparing transcription accuracy with and without the LSP context prompt.
3. What is the p99 latency of an LSP hover + documentSymbol request chain in a large TypeScript project (e.g. a 500-file monorepo)? If > 50 ms, the non-blocking timeout approach is essential.

## Risks and Unknowns

**Technical risks:**
- [HYPOTHESIS] LSP server availability is not guaranteed: the user may not have an LSP server running (running a plain text editor, or an LSP that has crashed). The capability must degrade gracefully to standard transcription when the LSP bridge returns `None`.
- [HYPOTHESIS] Different editors have incompatible extension mechanisms. Building bridges for Neovim and VS Code first covers ~60% of the target developer population, but JetBrains IDE users require a separate Java plugin that is out of scope for the initial implementation.

**External dependency risks:**
- [HYPOTHESIS] The VS Code companion extension requires separate publication to the VS Code Marketplace. Marketplace review and publication latency could delay the feature's availability to VS Code users by 1–2 weeks after the daemon release.
- [HYPOTHESIS] LSP server versions differ between projects; the JSON-RPC schema for `textDocument/documentSymbol` may return different structures depending on the language server implementation. The `LspContextProvider` must tolerate partial responses gracefully.

**Validation unknowns (require prototyping):**
- [HYPOTHESIS] Whether Whisper's `initial_prompt` conditioning actually improves transcription accuracy for code identifiers in controlled A/B testing. The mechanism is plausible but the effect size is unknown.
- [HYPOTHESIS] Whether injecting a 200-token context string into `initial_prompt` causes any performance regression in faster-whisper decode time on CPU. Must be measured empirically.

## Dependencies

**CapabilityCard dependencies:**
- cap-001 (Offline LLM Intent Routing) — LSP context is most valuable when the intent router can reason about it semantically. Without cap-001, the context improves transcription accuracy but does not enable code-aware command disambiguation. LSP integration can be built before cap-001 is complete; the two capabilities compose additively.

**External libraries / services:**
- `pygls >= 1.3.0` — Python LSP client library (MIT); provides the JSON-RPC transport layer for LSP connections.
- VS Code companion extension: TypeScript extension using the VS Code extension API — published separately to the Marketplace.

**Infrastructure requirements:**
- A running LSP server for the active editor. No additional hardware or cloud service.
- User's editor must be supported (Neovim with `nvim-lspconfig`, VS Code with any language extension, Emacs with `lsp-mode`).

## Scoring Rationale

- **user_pain: 5/5** — Transcription of code-specific vocabulary is the single biggest obstacle to using voice dictation for real coding work. Every developer who has tried voice coding has hit this wall. The pain is concrete, frequent, and blocking. [EVIDENCE src-002]
- **feasibility: 3/5** — [HYPOTHESIS] The LSP integration concept is sound, but the per-editor bridge implementations introduce significant engineering surface area. VS Code (companion extension) and Neovim are both achievable; broad editor coverage requires ongoing maintenance. The fastest-whisper `initial_prompt` injection is low risk. Score 3 reflects the per-editor bridging complexity.
- **novelty: 5/5** — [EVIDENCE src-001, src-002] No voice system in the survey or in any commercial product addresses code-context injection via LSP. This is the first voice tool to exploit the LSP's structured code understanding for transcription improvement.
- **production_value: 5/5** — [HYPOTHESIS] For the developer persona, this capability determines whether YazSes is a usable daily driver for coding or a dictation-only tool. Production value is maximum because it directly enables the highest-value use case.

**Priority rank:** 2
