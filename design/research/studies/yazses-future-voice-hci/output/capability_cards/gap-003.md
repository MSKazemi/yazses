# EMG Silent Speech Backend

---

## Capability Description

Open-plan offices, library studies, and shared workspaces make acoustic voice dictation impractical — speaking aloud disrupts others and exposes private content. Users in these contexts have no alternative to keyboard typing, regardless of how useful a voice daemon would otherwise be for them. This capability integrates electromyography (EMG) biosignal devices as a first-class input modality for YazSes, enabling users to articulate speech silently — mouth the words without producing audible sound — and have their intent recognised and injected into the active window.

Open-office workers who mouth commands into a wearable EMG device (headphone-form-factor electrodes or wrist EMG band) can use voice dictation at full volume in their head with zero acoustic output. The daemon treats the EMG device exactly like the acoustic microphone: hold-to-speak, command classification, text injection — the entire pipeline is unchanged.

Users do not need to install a separate application, learn new workflows, or change their typing habits. The EMG device becomes another way to trigger the same daemon they already use.

---

## Underlying Mechanism

**EMGBackend implementing the HotkeyBackend protocol:** The YazSes `HotkeyBackend` protocol (`platform/base.py`) defines `start()`, `stop()`, and `on_hold_start`/`on_hold_end` callbacks. The `EMGBackend` implements this protocol and maps gesture/command events from an EMG device to the hold-start and hold-end callbacks. For command-vocabulary devices (src-005: 10 discrete commands), each command label maps to an IPC method call. For full-text EMG input (src-006: transformer sEMG), the recognised text is directly injected via the existing injection pipeline. [HYPOTHESIS]

**Hardware-agnostic serial/USB device protocol:** The `EMGBackend` defines a simple, documented serial protocol that EMG hardware must implement to integrate with YazSes. The protocol is intentionally minimal: `HOLD_START`, `HOLD_END`, `COMMAND:<label>`, and `TEXT:<string>` messages over USB serial (115200 baud, 8-N-1). Manufacturers and researchers can add YazSes support to any device by implementing this 4-message protocol. Device-specific drivers (for OpenBCI, Meta EMG wristband, custom Arduino builds) are added as thin wrappers above this protocol layer. [HYPOTHESIS]

**Command vocabulary mapping via `EmgProfile`:** A new `EmgProfile` configuration object maps each recognised EMG command label (a string) to a `CommandIntent` or a raw text string. This profile is stored in the YazSes TOML config under `[emg]` and is edited by the user (or via a future calibration wizard). The 10-command vocabulary from src-005 maps to the 10 highest-frequency YazSes intents by default. [EVIDENCE src-005] 96% command classification accuracy is reported for a 10-command vocabulary in a headphone-form-factor wearable device at consumer form factor.

**Full-text EMG path (transformer sEMG):** For devices that perform full-text recognition on-device and emit decoded text strings (src-006 architecture), the `EMGBackend` receives `TEXT:<string>` messages and routes them into the same post-processing pipeline (disfluency filter → grammar classifier → dispatch) as acoustic transcription output. The injection and intent dispatch pipeline is unchanged; only the transcription source differs. [HYPOTHESIS]

## Evidence Basis

- [EVIDENCE src-005] Headphone-form-factor EMG achieves 96% accuracy on 10 discrete command labels in a consumer wearable form factor. This directly validates the feasibility of the command-vocabulary path in a device the target user would actually wear.
- [EVIDENCE src-006] Transformer-based sEMG full-text recognition achieves 10.1% personalised character error rate — approaching the accuracy of acoustic STT in quiet conditions. This validates the full-text injection path for users with access to full-text EMG hardware.
- [EVIDENCE src-007] EEG + EMG fusion in wearable hardware achieves sentence-level silent speech recognition in real-time wireless mode, confirming that the on-device processing and wireless transmission are feasible without a tethered lab setup.
- [EVIDENCE src-011] Interspeech 2025 dedicated a special session to biosignal-enabled spoken communication — community-level validation that EMG integration is a mature enough research direction to target for near-term product development.
- [HYPOTHESIS] Consumer EMG headphones from major hardware vendors (Meta, Snap successors) are 2–3 years from mainstream availability. Building the open-source integration layer now positions YazSes as the software target when hardware ships, capturing first-mover advantage without betting on a specific hardware vendor.

## User Value Proposition

**Target persona (primary):** Open-plan office developer or writer who wants to use voice dictation but cannot speak aloud in their shared workspace, and currently has no voice interface option.

**Target persona (secondary):** User with motor or speech disabilities who can benefit from silent EMG input as an alternative to acoustic speech, as part of a broader AAC workflow (gap-006).

**Current pain:** The acoustic hotkey model is all-or-nothing: the user can speak (and disrupt their workspace) or not speak at all. There is no intermediate option. Voice daemon tools including YazSes explicitly require audio input; there is no documented path from "I want to use voice dictation silently" to "it works." The user is blocked at the hardware interface level.

**Improvement this capability delivers:**
- Open-office users gain access to a voice interface where none existed before. The daemon operates identically whether the input is acoustic or EMG — same hotkey UX, same command vocabulary, same text injection. [HYPOTHESIS]
- Users who adopt EMG for command dispatch get 96% command recognition accuracy on the 10-command default vocabulary, matching acoustic STT accuracy for command-class utterances in quiet conditions. [EVIDENCE src-005]
- The hardware-agnostic protocol means users can bring their own EMG device (OpenBCI, DIY Arduino, future consumer devices) without waiting for first-party YazSes hardware support. [HYPOTHESIS]

**So that:** open-office workers and users with speech accessibility needs can use the full YazSes command and dictation pipeline silently, without modifying any other part of their workflow.

## Technical Approach

**Data model:** `EmgProfile` is a new configuration section in `config.py`: `{device_port: str, baud_rate: int = 115200, command_map: dict[str, str], mode: Literal["command", "full_text"] = "command"}`. The `command_map` maps device command labels to `CommandIntent` names or raw text strings. [HYPOTHESIS]

**API surface:** `EMGBackend` satisfies the `HotkeyBackend` protocol and is registered in `platform/factory.py` alongside the existing `evdev` and `pynput` backends. The daemon's `LOADING` state attempts to open the configured serial port; if the device is absent, the daemon falls back to the default hotkey backend (degraded-graceful). `yazses doctor` checks for the configured port and reports its status. [HYPOTHESIS]

**Integration points:**
- `platform/base.py HotkeyBackend`: `EMGBackend` implements this protocol exactly. No changes to the daemon state machine. [HYPOTHESIS]
- `platform/factory.py`: when `EmgConfig.device_port` is set, `EMGBackend` is returned instead of the default hotkey backend. [HYPOTHESIS]
- `config.py`: new `EmgConfig` dataclass within the top-level `Config`; TOML section `[emg]`. [HYPOTHESIS]
- `stt/faster_whisper.py` (full-text mode only): when the EMG device sends `TEXT:<string>`, the text bypasses the audio pipeline and enters the post-processing stage directly. [HYPOTHESIS]

**Key technical questions before coding:**
1. Does the USB serial approach work with consumer-grade EMG headphones that use proprietary Bluetooth stacks rather than USB CDC serial? If most consumer devices are Bluetooth-only, the protocol may need a BLE variant.
2. For the command-vocabulary mode, should the daemon emit a visual acknowledgement (tray notification) when an EMG command is received, to compensate for the absence of acoustic feedback?
3. How should the EMG device calibration (per-user muscle signal threshold) be handled — in the `yazses enroll` wizard or in device firmware?

## Risks and Unknowns

**Technical risks:**
- [HYPOTHESIS] Consumer EMG hardware is not yet standardised. The first version of the `EMGBackend` must be tested with OpenBCI Cyton (research-grade, USB, well-documented) as a proxy; porting to consumer devices will require iterative driver work as specific hardware ships.
- [HYPOTHESIS] EMG signal quality is highly user-dependent (muscle anatomy, electrode placement, sweat, motion artifacts). The 96% accuracy reported by src-005 was measured in controlled conditions; open-office environments introduce motion noise. Accuracy may degrade to 85–90% in realistic conditions without per-user calibration.

**External dependency risks:**
- [HYPOTHESIS] `pyserial >= 3.5` is the only external dependency required for the USB serial path. This is a stable, MIT-licensed library already used in many embedded Python projects. Risk is low.
- [HYPOTHESIS] Consumer EMG devices from major hardware vendors may require proprietary SDKs under non-open-source licenses. The YazSes hardware-agnostic protocol avoids coupling to any single vendor SDK, but providing first-party drivers for popular devices requires licensing review per device.

**Validation unknowns (require prototyping):**
- [HYPOTHESIS] Whether the 10-command vocabulary covers the most-used YazSes intents for open-office workers. An analysis of command distribution in the YazSes telemetry (if available) or a user survey is needed to validate the default command map.
- [HYPOTHESIS] Whether the full-text EMG path introduces perceptible latency compared to acoustic STT. The sEMG transformer (src-006) runs on-device; the transmission latency over USB serial at 115200 baud is < 1 ms per message, so overall latency is determined by the on-device inference speed of the EMG hardware.

## Dependencies

**CapabilityCard dependencies:**
- None — cap-003 is independent of cap-001 and cap-002. It can be developed in parallel on a separate branch. The `HotkeyBackend` protocol is already defined; no daemon core changes are required.

**External libraries / services:**
- `pyserial >= 3.5` — USB CDC serial communication (MIT license).
- Reference hardware: OpenBCI Cyton (8-channel EEG/EMG, USB dongle, open hardware) for development and testing.

**Infrastructure requirements:**
- USB port on the host machine (or BLE adapter for wireless variants).
- No additional compute: EMG command classification runs on the device; the daemon only receives labelled output strings.

## Scoring Rationale

- **user_pain: 4/5** — The inability to use voice dictation in shared workspaces blocks an entire user context (open-plan office), but this is a subset of the total YazSes user population rather than a universal pain. Score 4 rather than 5 because acoustic users are not affected. [HYPOTHESIS]
- **feasibility: 4/5** — [EVIDENCE src-005, src-006] The EMG accuracy and hardware exist at research-grade level today. The `HotkeyBackend` protocol abstraction makes the daemon integration straightforward. Score 4 rather than 5 because consumer hardware is not yet mainstream and per-device driver work is required.
- **novelty: 5/5** — [EVIDENCE src-011] No open-source desktop voice daemon has an EMG backend. This is a uniquely novel capability: YazSes would be the only voice tool that works silently out-of-the-box, with zero changes to the core pipeline. [HYPOTHESIS]
- **production_value: 4/5** — [HYPOTHESIS] Production value is high for the open-office and accessibility personas but does not affect acoustic-only users. Score 4 reflects the non-universal applicability; for users who need it, the value is complete (the alternative is no voice input at all).

**Priority rank:** 3
