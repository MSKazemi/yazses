# Offline LLM Intent Routing Layer

---

## Capability Description

YazSes today relies on 25 regex rules to classify voice commands. Natural phrasing that doesn't match a rule silently falls through as dictation, even when the user clearly intended a command. This capability adds a local small language model (SLM) intent routing layer that understands natural phrasing variants — "close this tab", "shut the browser", and "dismiss this window" all correctly resolve to the same window-close intent — without sending any audio or text to a cloud service.

Power-user developers who currently dictate on the command line gain the ability to express commands in natural speech instead of memorising the exact phrases the regex grammar accepts. The daemon becomes reliably responsive to how people actually speak rather than requiring users to speak like a command parser.

Users no longer need to mentally translate their intent into grammar-safe phrasing. Failed command classifications that silently produce unwanted text injection are eliminated for the vast majority of commands.

---

## Underlying Mechanism

**Three-tier routing stack:** The grammar regex classifier (existing) is retained as Tier 1 — sub-10 ms, deterministic, zero cost. When Tier 1 fails to match, the utterance passes to Tier 2: a locally-quantised SLM (Phi-3-mini-4k-instruct at 4-bit or TinyLlama-1.1B at 4-bit) prompted with the current `CommandIntent` vocabulary and a few-shot template. Tier 2 returns a classified intent (or `DICTATE` if none matches above threshold) within an estimated 100–300 ms on a developer laptop CPU. [EVIDENCE src-003] An optional Tier 3 cloud API ceiling may be toggled by the user for complex multi-step tasks — disabled by default; all locally-handled intents never leave the machine. [HYPOTHESIS]

**Quantised model inference via llama.cpp / ctransformers:** The SLM is loaded once at daemon startup via `llama-cpp-python` (CPU backend) and kept resident in memory. Inference is synchronous within the post-transcription pipeline stage. At 4-bit quantisation, Phi-3-mini-4k requires approximately 2 GB RAM; TinyLlama-1.1B requires approximately 700 MB. [EVIDENCE src-003] TinyLlama-1B at 4-bit quantisation demonstrated adequate accuracy on low-complexity speech-to-action intents; Phi-3-mini is the quality step-up for complex natural language variants.

**Intent prompt template:** The Tier 2 prompt is a structured few-shot template injected at daemon startup, derived from the `CommandsConfig.profiles` in `commands/profiles.py`. It lists all known `CommandIntent` enum values with natural language exemplars (3–5 per intent). The SLM is asked to return a single JSON object `{"intent": "<value>", "args": {…}, "confidence": 0.0–1.0}`. The daemon parses this JSON and routes accordingly; parse failures fall back to `DICTATE`. [HYPOTHESIS]

**Confidence gating:** A confidence threshold (default: 0.75, user-configurable in `CommandsConfig`) gates the SLM output. Below threshold, the utterance is treated as `DICTATE` rather than risking a misclassified command. The existing grammar rollback mechanism (`disfluency filter`) becomes the fallback for SLM-classified commands as well. [HYPOTHESIS]

## Evidence Basis

- [EVIDENCE src-003] The only paper in the survey to explicitly demonstrate offline LLM intent routing: TinyLlama-1.1B at 4-bit quantisation operates on edge hardware without cloud connectivity and covers low-complexity speech-to-action intents with adequate accuracy. This is direct proof-of-concept validation that Tier 2 is technically feasible on consumer CPU hardware.
- [EVIDENCE src-002] VoiceBench shows that instruction-following failure (not transcription error) is the primary quality gap in all surveyed voice systems, including cloud-connected models. An intent routing layer directly addresses this gap.
- [EVIDENCE src-001] All LLM-mediated voice systems in the XR multimodal survey are cloud-connected; offline LLM voice routing does not yet exist as a deployed product. This confirms the novelty and absence of competition.
- [EVIDENCE src-009] LLM-driven NPC systems require cloud LLMs for semantic understanding — they identify offline NPC dialogue as an open problem. The same cloud dependency applies to desktop voice intent routing.
- [HYPOTHESIS] Phi-3-mini-4k-instruct (Microsoft, 3.8B parameters, 4-bit) is the stronger choice for complex phrasing variants; TinyLlama-1.1B is the fallback for extremely memory-constrained environments. Both are Apache-2.0 licensed. Exact latency and accuracy tradeoffs on the YazSes intent vocabulary require a benchmarking spike.

## User Value Proposition

**Target persona:** Power-user developer on Linux or macOS who has tried voice dictation but abandoned it because command recognition was too brittle to trust in a fast-moving workflow.

**Current pain:** The user must remember exact grammar phrases ("new file", not "create a new file", not "make a file") or accept that the daemon will inject raw text instead of executing a command. When the grammar misclassifies, the error is silent — unwanted text appears in the editor. After three such errors per session, most users disable the grammar and fall back to dictation-only mode, losing the command-dispatch value.

**Improvement this capability delivers:**
- Natural phrasing variants of all 25 existing intents succeed without re-learning — estimated >95% coverage of natural phrasing for known intents, vs. ~80% today with regex alone. [HYPOTHESIS]
- Silent command misclassification eliminated for known intents — the confidence gate ensures the SLM prefers `DICTATE` over a wrong command when uncertain. [HYPOTHESIS]
- Zero cloud dependency and zero additional hardware: the SLM runs on the same CPU used for faster-whisper, adding one extra resident process at daemon startup. [EVIDENCE src-003]

**So that:** the user can speak voice commands naturally without consulting the grammar reference card, and trust that an unrecognised utterance will become dictated text rather than a misexecuted command.

## Technical Approach

**Data model:** The existing `CommandIntent` enum and `dispatch.py` routing table are the output target for all three tiers; Tier 2 adds no new data model. The `CommandsConfig` dataclass in `config.py` gains two new fields: `slm_model_path: str` (path to the GGUF model file, default resolved from XDG cache) and `slm_confidence_threshold: float = 0.75`. [HYPOTHESIS]

**API surface:** The SLM intent router is an internal module (`commands/slm_router.py`) with a single public function `classify(transcript: str, profile: GrammarProfile) -> CommandIntent | None`. It is called by `grammar.py` after regex classification fails, before `dispatch.py` receives the intent. No IPC or CLI surface changes are required. [HYPOTHESIS]

**Integration points:**
- `commands/grammar.py`: after regex classification returns `None`, `slm_router.classify()` is called. [HYPOTHESIS]
- `config.py CommandsConfig`: two new fields for model path and confidence threshold. [HYPOTHESIS]
- `core/daemon.py LOADING` state: SLM model is loaded once during daemon initialization; if the GGUF file is absent, Tier 2 is skipped silently (degraded-graceful). [HYPOTHESIS]
- `pyproject.toml`: `llama-cpp-python >= 0.3.0` added as an optional dependency (`[extras] slm`). [HYPOTHESIS]

**Key technical questions before coding:**
1. Does Phi-3-mini-4k at 4-bit meet the < 300 ms p99 latency target on a 4-core developer laptop? Requires a benchmarking spike with the actual YazSes intent vocabulary prompt template.
2. What is the optimal few-shot prompt structure for the intent classification task? Few-shot template quality significantly affects SLM accuracy on this narrow domain.
3. Should the SLM run in a background thread (non-blocking) with a fallback to `DICTATE` on timeout, or in-line (blocking the transcription pipeline)? Non-blocking is more robust but adds engineering complexity.

## Risks and Unknowns

**Technical risks:**
- [HYPOTHESIS] SLM inference latency may exceed 300 ms p99 on low-end laptops (e.g. 2-core 8 GB RAM), making the Tier 2 pause perceptible and annoying. Mitigation: implement async non-blocking inference with a configurable timeout that falls through to `DICTATE` if exceeded.
- [HYPOTHESIS] The GGUF model file (700 MB for TinyLlama, ~2 GB for Phi-3-mini) is too large to bundle in the YazSes package. Users must download it separately. This creates a first-run friction that could prevent adoption. Mitigation: `yazses doctor` detects the missing model and provides a single-command download instruction; the feature is disabled (not broken) without the model.

**External dependency risks:**
- [HYPOTHESIS] `llama-cpp-python` wheels are platform-specific and have had version compatibility issues in the past. The build matrix (Linux x86_64, macOS arm64, Windows x86_64) must be validated in CI. Mitigation: pin the `llama-cpp-python` version; document alternative backends (ctransformers, mlx-lm for Apple Silicon).
- [HYPOTHESIS] Phi-3-mini is Apache-2.0 licensed. TinyLlama is Apache-2.0 licensed. These are currently correct but license changes in future versions would require re-evaluation. Pin to specific model versions (GGUF with SHA256 hash) in the download manifest.

**Validation unknowns (require prototyping):**
- [HYPOTHESIS] Whether the few-shot prompt template generalises to novel phrasing variants not included in the template. This requires a blind evaluation on a held-out test set of natural voice command variants.
- [HYPOTHESIS] Whether per-profile grammar injection (different intents active in different editors) works correctly with the SLM prompt template. The profile-switching mechanism must be replicated in the Tier 2 prompt at runtime.

## Dependencies

**CapabilityCard dependencies:**
- None — cap-001 is the foundational capability. cap-002 and gap-004 depend on cap-001.

**External libraries / services:**
- `llama-cpp-python >= 0.3.0` — CPU inference backend for GGUF quantised models; Apache-2.0.
- Model: Phi-3-mini-4k-instruct-Q4_K_M.gguf (~2.2 GB) or TinyLlama-1.1B-Chat-v1.0.Q4_K_M.gguf (~700 MB) — Apache-2.0.

**Infrastructure requirements:**
- Daemon host: >= 4 GB RAM (TinyLlama variant) or >= 6 GB RAM (Phi-3-mini variant) at runtime. Existing developer laptops satisfy this requirement.
- Disk: >= 2.5 GB free in the YazSes cache directory (`~/.cache/yazses/models/`) for the GGUF file.

## Scoring Rationale

- **user_pain: 5/5** — The inability to use natural phrasing for voice commands is the most-cited reason users disengage from grammar-based voice daemons. gap-001 directly addresses the primary documented failure mode of every voice system in the survey. [EVIDENCE src-002, src-010]
- **feasibility: 4/5** — [HYPOTHESIS] The core technology (TinyLlama/Phi-3-mini at 4-bit) is validated by src-003; the integration with YazSes grammar and dispatch is straightforward. Latency is the main uncertainty; the spike will confirm or refine this score.
- **novelty: 5/5** — [EVIDENCE src-001, src-002, src-009] No voice daemon in the survey combines offline-first architecture with LLM-quality semantic intent routing. This is a genuinely new capability class.
- **production_value: 5/5** — [HYPOTHESIS] This capability directly determines whether YazSes is usable as a primary voice interface for power users. Without it, the daemon is useful only to users who memorise grammar phrases. With it, the daemon becomes a natural-language voice interface that works offline — a combination that does not yet exist.

**Priority rank:** 1
