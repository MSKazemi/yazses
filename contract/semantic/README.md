# The semantic layer — meaning, not just parity

`../vectors/` pins **parity**: every implementation delivers the same string. This
directory pins **meaning**: the delivered string still says what the speaker said.

Both are necessary. Only one of them is safe to generate.

---

## Why this layer exists

Parity vectors are generated by running the shipped Python. That is the right way to
stop cross-platform drift, and it has a blind spot its own guard cannot see: a desktop
change can update the implementation, the generator and the golden data in one step. The
vectors stay green, CI stays green, and every platform is now wrong in the same way.

> Post-processing may simplify form, but it must not silently erase or invert a
> distinction that changes what a downstream reader should understand or do.

This layer is the independent anchor for that rule. It was proposed by **@YossiMH** in
the mobile design review ([#98](https://github.com/MSKazemi/yazses/issues/98)) and
adopted as ADR-MOB-008 §8.

It matters because YazSes is used for patient notes, meeting minutes and source
interviews, where the dangerous failure is not garbled output — that gets corrected —
but *plausible* output. `she is stable` is a perfectly well-formed sentence. Nothing
tells the reader that `sort of` was deleted.

## The rule that makes it work

**Nothing here is ever regenerated from the implementation.** `expected` is what a human
says the user must receive. When the code and this directory disagree, the code is what
changes — or the case is demoted to a `known-gap` with an issue link, in the same PR,
reviewed as the behaviour change it is.

`tests/test_semantic_invariants.py` enforces this literally: it fails if
`scripts/gen-contract-vectors.py` so much as mentions this directory.

## Files

```
contract/semantic/
  dimensions.json   the conserved dimensions + their extraction patterns
  invariants.json   the cases
```

`dimensions.json` is a deliberately tiny extractor — patterns in, a value out. It is not
an NLP model and must not grow into one; it only has to be exact on the cases that cite
it, and small enough that Kotlin and Swift can reimplement it in a few dozen lines.

| Dimension | Question it answers | Failure it catches |
|---|---|---|
| `polarity` | asserted or denied? | `did` delivered as `did not` |
| `certainty` | hedged or committed? | a guess promoted to a fact |
| `time` | when? | `now` delivered as `yesterday` |
| `actor` | who? | an act reassigned to the wrong person |
| `quantity` | how many? | `fifteen` delivered as `fifty` |
| `unit` | of what? | a dose that keeps its number and loses `mg` |
| `request_or_refusal` | report, instruction, or refusal? | `do not stop` delivered as `stop` |
| `correction_marker` | which value supersedes? | a correction delivered as a contradiction |
| `assessment` | what judgement? | `not right` delivered as a fragment |

## The two checks

**Invariant** — the delivered text must still read with the declared dimensions.
`must_preserve` catches loss; `must_not_acquire` catches inversion and invention.

**Minimal pair** — two utterances differing in exactly one consequential dimension must
not collapse to the same delivered text. This is the check no per-case assertion can
make. Each output can look entirely plausible on its own:

```
she is stable          -> "she is stable"
she is sort of stable  -> "she is stable"     <- the distinction is gone
```

Both outputs are fine sentences. Only the pair proves something was destroyed.

## Known gaps

A case with `status: "known-gap"` is an invariant the shipped filter does **not**
satisfy. It is strict-xfail, so:

- the suite is green while the gap is recorded, not hidden;
- the runner separately asserts the gap still reproduces *exactly as documented*;
- the moment somebody fixes the code, the suite goes **red** asking for the case to be
  promoted to `holds`.

A gap can therefore be recorded, but never forgotten and never silently blessed. There
are five today, all from one cause — [#146](https://github.com/MSKazemi/yazses/issues/146).

## Adding a case

The bar is higher than for a parity vector, on purpose. A case belongs here only if
**getting it wrong would mislead a reader about something consequential**, and if you
can name which dimension carries that consequence. Everything else is a parity vector
and belongs in `../vectors/`.

1. Add the case to `invariants.json` with a `description` that says what a reader would
   wrongly conclude if the invariant broke.
2. Add its minimal-pair partner. A dimension you cannot build a pair for is usually a
   dimension you have not pinned down.
3. Run `uv run python -m pytest tests/test_semantic_invariants.py`.
4. If it fails, **do not adjust `expected` to match the output.** That is the one move
   this entire layer exists to prevent. Either the code is wrong, or your case is —
   decide which, and say so in the PR.

## For Kotlin and Swift implementations

Read both files as test data alongside `../vectors/`. Your module is not done when the
parity vectors are green; it is done when the parity vectors are green **and** these
invariants hold. "Match Python" is a weaker promise than "preserve these meanings", and
if the two ever conflict, this directory wins.
